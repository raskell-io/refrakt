# Database

Refrakt supports PostgreSQL and SQLite. The database choice is made at
project creation time and affects generated repos and migrations.

## Setup

### PostgreSQL

```bash
refrakt new my_app --db postgres
```

This adds `pog` to dependencies and generates a `repo.gleam` that
connects via URL, taken from `DATABASE_URL` or a local default:

```gleam
// src/<app>/data/repo.gleam
pub fn connect(cfg: Config) -> Result(pog.Connection, Nil) {
  let default_url = case cfg.env {
    config.Test -> "postgres://postgres@localhost:5432/my_app_test"
    _ -> "postgres://postgres@localhost:5432/my_app_dev"
  }
  let db_url = envoy.get("DATABASE_URL") |> result.unwrap(default_url)

  let pool_name = process.new_name(prefix: "my_app_db")
  use db_config <- result.try(pog.url_config(pool_name, db_url))
  case pog.start(db_config) {
    Ok(_started) -> Ok(pog.named_connection(pool_name))
    Error(_) -> Error(Nil)
  }
}
```

Create the database:

```bash
createdb my_app_dev
createdb my_app_test
```

### SQLite

```bash
refrakt new my_app --db sqlite
```

This adds `sqlight` to dependencies and generates a `repo.gleam` with
a path helper:

```gleam
// src/<app>/data/repo.gleam
pub fn database_path(cfg: Config) -> String {
  case cfg.env {
    config.Test -> ":memory:"
    _ -> "my_app.db"
  }
}
```

No external database server needed. The SQLite file is created
automatically on first use.

## Repos

Repos are generated by `refrakt gen resource`. They use raw SQL
with typed decoders.

### PostgreSQL repos (Pog)

```gleam
/// One page of posts, newest first, and how many there are.
pub fn list(db: pog.Connection, params: paginate.Params) -> paginate.Page(Post) {
  let items =
    pog.query("SELECT id, title, body, published FROM posts ORDER BY id DESC LIMIT $1 OFFSET $2")
    |> pog.parameter(pog.int(params.per_page))
    |> pog.parameter(pog.int(paginate.offset(params)))
    |> pog.returning(post_decoder())
    |> pog.execute(db)
    |> result.map(fn(r) { r.rows })
    |> result.unwrap([])
  let total = case
    pog.query("SELECT COUNT(*) FROM posts")
    |> pog.returning(decode.at([0], decode.int))
    |> pog.execute(db)
  {
    Ok(pog.Returned(rows: [count], ..)) -> count
    _ -> 0
  }
  paginate.page(items, params, total)
}

pub fn get(db: pog.Connection, id: Int) -> Result(Post, Nil) {
  pog.query("SELECT id, title, body, published FROM posts WHERE id = $1")
  |> pog.parameter(pog.int(id))
  |> pog.returning(post_decoder())
  |> pog.execute(db)
  |> result.replace_error(Nil)
  |> result.try(fn(r) {
    case r.rows { [item] -> Ok(item)  _ -> Error(Nil) }
  })
}
```

Postgres uses `$1`, `$2` parameter placeholders and `pog.parameter()`
for type-safe parameter binding.

### SQLite repos (Sqlight)

```gleam
pub fn list(db_path: String, params: paginate.Params) -> paginate.Page(Task) {
  use conn <- sqlight.with_connection(db_path)
  let items = case
    sqlight.query(
      "SELECT id, title, completed FROM tasks ORDER BY id DESC LIMIT ? OFFSET ?",
      on: conn,
      with: [sqlight.int(params.per_page), sqlight.int(paginate.offset(params))],
      expecting: task_decoder(),
    )
  {
    Ok(rows) -> rows
    Error(_) -> []
  }
  let total = case
    sqlight.query("SELECT COUNT(*) FROM tasks", on: conn, with: [], expecting: decode.at([0], decode.int))
  {
    Ok([count]) -> count
    _ -> 0
  }
  paginate.page(items, params, total)
}
```

SQLite uses `?` parameter placeholders and `sqlight.int()`,
`sqlight.text()` for parameter binding. Boolean fields use
`sqlight.decode_bool()` since SQLite stores booleans as integers.

### Pagination

`list` returns one page (`refrakt/paginate`): `paginate.Params(page:,
per_page:)` goes in, and a `paginate.Page(item)` with the page's
`items`, the `total` count, `total_pages`, `has_previous` and `has_next`
comes out. The handler picks the page from the query string
(`paginate.page_number(req)` for HTML, `paginate.from_request_with(req,
per_page:)` for the JSON API, which also reads `?per_page=`); the page
size is `pub const per_page` in the handler.

Generated repos page with `LIMIT`/`OFFSET`: it works with any `ORDER
BY`, lets visitors jump to any page and gives a total for "Page 2 of 5".
The database still reads past the skipped rows, so very deep pages of
very large tables get slow. For those, or for infinite scrolling,
paginate by key instead: `WHERE id < $1 ORDER BY id DESC LIMIT $2`, with
the last id of the previous page.

To load every row (an export, say), add your own function next to
`list`:

```gleam
pub fn all(db: pog.Connection) -> List(Post) {
  pog.query("SELECT id, title, body, published FROM posts ORDER BY id DESC")
  |> pog.returning(post_decoder())
  |> pog.execute(db)
  |> result.map(fn(r) { r.rows })
  |> result.unwrap([])
}
```

## Decoders

Both backends use positional decoders (field index, not name):

```gleam
fn post_decoder() -> decode.Decoder(Post) {
  use id <- decode.field(0, decode.int)
  use title <- decode.field(1, decode.string)
  use body <- decode.field(2, decode.string)
  use published <- decode.field(3, decode.bool)
  decode.success(Post(id: id, title: title, body: body, published: published))
}
```

The field order must match the `SELECT` column order.

An `optional(T)` field is a nullable column. The repo decodes it with
`decode.optional(...)` and binds it with `pog.nullable` /
`sqlight.nullable`, so `None` is `NULL`:

```gleam
use capacity <- decode.field(2, decode.optional(decode.int))
// ...
|> pog.parameter(pog.nullable(pog.int, params.capacity))
```

## Relations (`--belongs-to`)

```bash
refrakt gen resource posts title:string body:text
refrakt gen resource comments body:text --belongs-to posts
```

The parent resource must exist (its `domain/post.gleam` and
`data/post_repo.gleam` with `get`); otherwise the command says so and
writes nothing. `--belongs-to posts` gives the child:

- **A foreign key.** A `post_id` field and column, indexed:

  ```sql
  CREATE TABLE comments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    body TEXT NOT NULL,
    post_id INTEGER NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    ...
  );
  CREATE INDEX comments_post_id_index ON comments (post_id);
  ```

  **`ON DELETE CASCADE`**: deleting a post deletes its comments. A
  child usually means nothing without its parent, and the alternative,
  `RESTRICT`, would make the generated delete button fail on any post
  with comments. Change it in the migration before running it if you
  want to keep children (`ON DELETE RESTRICT`, or `SET NULL` with an
  `optional(int)` column).

- **`comment_repo.list_for_post(db, post_id)`**: the comments of one
  post, oldest first. Unlike `list`, it is not paginated: it returns
  every comment of the post, for the post's page. Add `LIMIT`/`OFFSET`
  as `list` does if a parent can have very many children.
- **`comment_repo.post_options(db)`** (HTML resources): `#(id, label)`
  pairs for the form's select, labelled with the post's first string
  field or `Post #<id>`.
- **A parent check.** `create` and `update` look the post up with
  `post_repo.get` after the form or JSON body is valid; a missing post
  is a 422 (`post_id`: "Post does not exist"), in HTML and in `--api`
  mode alike.
- **A select of posts** in the form instead of a number input, and a
  link to the post on the comment's show page. `/comments/new?post_id=<id>`
  preselects the post.
- **The comments on the post's page.** `web/components/comment_list.gleam`
  renders a list of comments with links and a "New Comment" link. When
  `web/post_handler.gleam` still renders `post_views.show_view(item)` as
  generated, the CLI wraps it:

  ```gleam
  element.fragment([
    post_views.show_view(item),
    comment_list.render(item.id, comment_repo.list_for_post(ctx.db, item.id)),
  ])
  ```

  A second child is added to the same fragment. If the handler was
  changed (or the parent is an `--api` resource), the CLI leaves it
  alone and prints the lines to add.

Routes stay flat: `/comments`, `/comments/:id` and so on, as for any
resource. There are no nested `/posts/:id/comments` routes; the post is
a field of the comment, chosen in the form or preselected with
`?post_id=`. Add nested routes to `router.gleam` by hand if you need
them, for example `["posts", id, "comments"], http.Get ->` a handler
that calls `comment_repo.list_for_post`.

### SQLite foreign keys

SQLite enforces foreign keys, and so `ON DELETE CASCADE`, only on a
connection that runs `PRAGMA foreign_keys = ON`. Every SQLite repo
generated since 0.6 runs it in `delete`:

```gleam
pub fn delete(db_path: String, id: Int) -> Result(Nil, Nil) {
  use conn <- sqlight.with_connection(db_path)
  use _ <- result.try(
    sqlight.exec("PRAGMA foreign_keys = ON", conn)
    |> result.replace_error(Nil),
  )
  // DELETE FROM ...
}
```

A parent repo generated by an older version lacks it; `gen resource
--belongs-to` then prints the line to add to its `delete`. The other
repo functions do not turn foreign keys on: the generated handlers
check the parent before they write. Postgres always enforces foreign
keys.

## Migrations

Migrations are plain SQL files in `src/<app>/data/migrations/`.

### Generate a migration

```bash
refrakt gen migration add_email_to_posts
```

Creates: `src/<app>/data/migrations/002_add_email_to_posts.sql`

### Resource migrations (auto-generated)

`refrakt gen resource` creates the migration automatically.

PostgreSQL:

```sql
CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  published BOOLEAN NOT NULL,
  inserted_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

SQLite:

```sql
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  completed INTEGER NOT NULL,
  inserted_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

Columns are `NOT NULL` except for `optional(T)` fields. A
`--belongs-to` field adds `REFERENCES <parents>(id) ON DELETE CASCADE`
and an index (see [Relations](#relations---belongs-to)).

### Running migrations

```bash
refrakt migrate
```

The first run generates `src/<app>/migrate.gleam`, which connects to
the database and applies every file not yet listed in the `_migrations`
table, in number order.

A migration file can hold as many statements as you like:

```sql
CREATE TABLE comments (
  id SERIAL PRIMARY KEY,
  post_id INTEGER NOT NULL REFERENCES posts (id),
  body TEXT NOT NULL
);
CREATE INDEX comments_post_id_index ON comments (post_id);
```

**Each migration runs in one transaction**, together with the
`_migrations` row that records it. If any statement fails, the whole
file is rolled back, nothing is recorded, and `refrakt migrate` stops
and prints the file name and the database error:

```
  003_add_comments.sql ...
Error: Migration 003_add_comments.sql failed and was rolled back: relation "postz" does not exist (undefined_table, SQLSTATE 42P01)
  in statement: CREATE TABLE comments (...)
```

Fix the file and run `refrakt migrate` again. Migrations that already
succeeded stay applied. Both Postgres and SQLite roll back DDL
(`CREATE TABLE`, `CREATE INDEX`, ...), so a failed migration leaves no
half-created tables behind.

Because of the transaction, a migration file must not contain its own
`BEGIN`/`COMMIT`, and statements that cannot run inside a transaction
do not work in a migration: on Postgres `CREATE INDEX CONCURRENTLY`,
`CREATE DATABASE` and `VACUUM`; on SQLite `VACUUM` and
`PRAGMA foreign_keys` (which is ignored inside a transaction).

**Postgres** runs one statement per query, so the generated module
splits each file with `migrate.split_statements`. It splits on `;`
outside of string literals (`'...'`, `E'...'`), quoted identifiers
(`"..."`), comments (`--`, `/* */`), dollar-quoted bodies (`$$ ... $$`,
`$tag$ ... $tag$`) and `BEGIN ATOMIC ... END` function bodies, so
functions, triggers and `DO` blocks work as written:

```sql
CREATE FUNCTION touch_updated_at() RETURNS trigger AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER posts_touch BEFORE UPDATE ON posts
  FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
```

**SQLite** runs each file as is with `sqlight.exec`, which handles
several statements (including `CREATE TRIGGER ... BEGIN ... END`)
itself, between `BEGIN` and `COMMIT`.

You can also apply a file by hand, outside the runner (it is then not
recorded in `_migrations`):

```bash
psql my_app_dev < src/my_app/data/migrations/001_create_posts.sql
sqlite3 my_app.db < src/my_app/data/migrations/001_create_tasks.sql
```

### Programmatic migration runner

The generated `migrate.gleam` calls `migrate.run` with two callbacks,
so the library stays independent of the database driver:

```gleam
import refrakt/migrate

let result = migrate.run(
  "src/my_app/data/migrations",
  // Run a SELECT, return the first column of each row
  query: query_strings,     // fn(String) -> Result(List(String), String)
  // Run SQL scripts in order in one transaction; roll back on error
  transaction: transaction, // fn(List(String)) -> Result(Nil, String)
)
// -> Ok(number_of_migrations_applied) or Error(message)
```

The runner tracks applied migrations in a `_migrations` table and
only runs pending ones. For each pending file it calls `transaction`
with the file's SQL and the `INSERT` into `_migrations`, so both commit
or roll back together. Look at the generated module for the Postgres
(`pog.transaction`) and SQLite (`BEGIN`/`COMMIT`/`ROLLBACK`) versions.

`migrate.run_from_directory`, used by modules generated before 0.5, is
deprecated: it runs each file as a single query without a transaction.

## Adding a database later

If you started without `--db` and want to add one:

1. Add the dependency: `gleam add pog` or `gleam add sqlight`
2. Create `src/<app>/data/repo.gleam` (copy from a generated project)
3. Add a `db` (or `db_path`) field to `Context` in `context.gleam`
4. Connect in `src/<app>.gleam` and pass to the context
5. Use `refrakt gen resource` — it auto-detects the DB from `gleam.toml`

## Writing queries manually

You own the repo files. Add custom queries alongside the generated ones:

```gleam
pub fn list_published(db: pog.Connection) -> List(Post) {
  pog.query("SELECT id, title, body, published FROM posts WHERE published = $1 ORDER BY id DESC")
  |> pog.parameter(pog.bool(True))
  |> pog.returning(post_decoder())
  |> pog.execute(db)
  |> result.map(fn(r) { r.rows })
  |> result.unwrap([])
}
```

There is no query builder or ORM. SQL is readable, debuggable, and
doesn't hide what's happening.
